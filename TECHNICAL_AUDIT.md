## Состояние репозитория и границы работы

Проверены status, log, remotes и целостность Git. `origin` указывает на запрошенный GitHub-репозиторий. Ветка создана от исходного `main`. Commit, push, merge, изменение тегов и запуск GitHub Actions не выполнялись. Файлы проекта в `sources/` не затрагивались. Первоначальная копия из служебной папки перенесена в выбранный пользователем каталог; второй рабочей копии не осталось.

Аудит не меняет production-код. Локальные сборки, виртуальное окружение и диагностические данные находятся в игнорируемых каталогах. Проверки доступа выполнялись только на искусственных заметках, без пользовательского vault и без публикации сервера в сеть.

## Архитектура

- Корневой `package.json` управляет командами разработки. `pnpm-workspace.yaml` включает только `apps/*`: Obsidian-плагин устанавливается отдельно через npm и имеет собственный package-lock.
- `python/`: Python 3.11+, Typer CLI, MCP SDK, Starlette/Uvicorn, SQLite + Chroma, sentence-transformers/PyTorch, watchdog, локальный LLM через llama-cpp-python. Бизнес-логика вынесена в `core/`.
- Основной сценарий: `obsidian-plugin/` запускает один vault-server для хранилища и общается с admin REST. Внешний клиент получает scope-токен и подключается к `/sse`.
- Старый сценарий: MCP stdio и Electron/React-приложение работают с отдельными project-centric настройками и индексами. Это не прокси к scope-серверу Obsidian.
- `.github/workflows/plugin-release.yml` собирает ZIP Obsidian-плагина с автономным Python executable для шести платформ. Electron installer этот workflow не собирает.

Архитектуру можно сохранить. Основные изменения нужны в упаковке, transport/auth и согласовании правил доступа между интерфейсом и сервером.

## Windows и GitHub release: причины

### Главный воспроизведённый runtime-дефект: из сборки исключён unittest

Полная исходная Windows-сборка через `scripts/build-plugin-sidecar.ps1` завершилась успешно. Полученный `.exe` запустил vault-server и начал индексировать искусственную заметку. Затем произошла ошибка:

```text
core/embeddings.py -> import torch
 torch.distributed.config -> torch.utils._config_module -> import unittest
ModuleNotFoundError: No module named 'unittest'
```

Причина: `python/obsidian-context-mcp.spec:95` явно исключает `unittest`, хотя установленный PyTorch 2.12.0+cpu использует его в runtime. В обычном Python-окружении torch, sentence-transformers, Chroma, ONNX Runtime и llama_cpp импортировались успешно. Ошибка возникает до загрузки модели; она не вызвана offline-режимом smoke-проверки.

Минимальное исправление: убрать ошибочное исключение `unittest`, затем пересобрать и проверить полный импорт/индексацию. Аналогичное исключение `torch.backends.cudnn` требует проверки по фактическим imports; его нельзя автоматически считать ненужным только из-за CPU-режима. Устранение первой ошибки ещё не доказывает отсутствие последующих проблем упаковки.

Сервер при провалившейся индексации продолжает отвечать `/health` = 200. `AdminApi.health` проверяет лишь существование HTTP-процесса, а `Indexer.run` завершает job как COMPLETED даже при files_failed. Поэтому плагин может показывать запущенный сервер с неработающим поиском. Нужны отдельные readiness/ошибки индексации и smoke, проверяющий результат, а не только код процесса или health.

### Дополнительный frozen CLI дефект

`python/src/obsidian_context_mcp/__main__.py:14` считает любой первый аргумент, начинающийся с `-`, служебным multiprocessing-запуском. Поэтому `.exe --help` тихо заканчивается с кодом 0, не вызывая CLI. Контрольный `vault-server --help` действительно печатает справку. Нужно распознавать только реальные worker/bootstrap аргументы; тестировать содержимое справки, а не только exit 0.

Каждый старт onefile executable на этой машине занимал десятки секунд (root help 18.7 s, subcommand help 23.8 s), включая распаковку. Это локальное измерение, а не универсальная характеристика всех Windows-машин.

### 1. Windows-скрипт может объявить успех после провала native-команды — воспроизведено

`scripts/build-plugin-sidecar.ps1:19-23` запускает uv/PyInstaller, но не проверяет `$LASTEXITCODE`. `$ErrorActionPreference = 'Stop'` в используемом Windows PowerShell сам по себе не останавливает выполнение при ненулевом коде внешней программы. Далее проверяется только существование executable, без проверки свежести.

Изолированная копия исходного скрипта получила ошибку установки 23 и ошибку `No module named PyInstaller`. При наличии фиктивного старого executable скрипт всё равно скопировал его и завершился с кодом 0. Аналогичный контроль отсутствует у npm в `build-plugin-release.ps1` и у upload в `upload-release-asset.ps1`.

Минимальное исправление: единый небольшой helper для запуска native-команд с проверкой кода выхода; чистый целевой каталог или проверка артефакта текущего запуска; не использовать committed main.js как молчаливую замену провалившейся сборке.

### 2. Python lock не соответствует манифесту — воспроизведено

`python/pyproject.toml` имеет версию 0.2.7 и требует llama-cpp-python, uvicorn, starlette. В `python/uv.lock` запись самого проекта осталась на 0.1.0, llama-cpp-python вообще отсутствует; Intel Mac overrides также не соответствуют lock. Uvicorn/Starlette приходят транзитивно, что маскирует часть рассогласования.

Release-скрипты используют `uv pip install -e .[dev]`, обходя lock. PyInstaller тоже устанавливается без фиксации версии. Поэтому одинаковый commit способен собираться с разными SDK, ML-библиотеками и hooks. Просто добавить `--frozen` нельзя: сначала нужно привести lock в соответствие и согласовать CPU wheels для каждой платформы.

### 3. CI проверяет упаковку, но не работоспособность — подтверждено workflow

В workflow нет pytest, lint/typecheck, запуска `.exe --help`, проверки vault-server, MCP handshake или индексации искусственной заметки. Плагин собирается через esbuild, который не выполняет проверку типов. Поэтому success workflow не равен рабочему плагину.

При ручном запуске параметр `tag` применяется к публикации, но `actions/checkout` не получает соответствующий ref; версия ZIP берётся из manifest. Можно опубликовать артефакт другого commit/версии в существующий release. Публикация идёт отдельно из каждой matrix job, поэтому release может оказаться частично обновлённым.

Полученные через GitHub API факты:

- [Последний доступный Plugin release run](https://github.com/hotterinc/Cursor_MCP_for_Obsidian/actions/runs/27574934343) — success для всех шести платформ, собран commit `9d9c40e`, а не текущий `b95ef38`.
- Tag `v0.2.7` указывает на `15f2d93`, отличающийся от commit этого workflow.
- [Release v0.2.7](https://github.com/hotterinc/Cursor_MCP_for_Obsidian/releases/tag/v0.2.7) содержит одновременно свежий linux-x64 ZIP и более старые `.zip.aa/.zip.ab`. Пользователь может скачать несовместимый набор артефактов.
- Подробные job logs недоступны: API возвращает 410. Причину исторического сбоя по этим логам установить нельзя. Доступные статусы не показывают текущего падения Windows job.

Минимальное исправление: проверять совпадение ref/tag/manifest, собирать из зафиксированных зависимостей, добавлять smoke-проверки готового binary и публиковать проверенный набор артефактов после успешной матрицы. Старые assets не удалялись в рамках аудита.

### 4. Windows-пути Electron и команда dev некорректны

- `package.json:9`: Unix `env -u` не работает в стандартной Windows shell; воспроизведено.
- `apps/desktop/src/main/pythonSidecar.ts:83-89`: PATH собирается через `:` и содержит `.venv/bin`; на Windows нужен разделитель `;` и `.venv/Scripts`.
- `pythonSidecar.ts:100`: имя binary записано без `.exe`, но это само по себе не доказанная ошибка: локальный Node spawn успешно нашёл Windows executable без указания расширения. Явное платформенное имя можно унифицировать при исправлении launcher.
- `scripts/build-python.sh`: PyInstaller не объявлен как dependency, используется упрощённая конфигурация вместо plugin spec; неудачное копирование подавляется `|| true`.
- Корневое `package:desktop` запускает только electron-builder; самостоятельной подготовки свежего Python sidecar в нём нет.

Минимальное исправление: платформонезависимый launcher, `path.delimiter`, Windows-имя binary, единый проверенный способ сборки sidecar для плагина и Electron.

### 5. Дополнительные проблемы упаковки

Windows release-script игнорирует `SKIP_PLUGIN_UI=1` и повторяет npm install/build из workflow. Используется npm install вместо npm ci. Для крупных Windows ZIP не предусмотрен аналог Unix split; используемый Compress-Archive документирует ограничение 2 GB на файл ([Microsoft](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.archive/compress-archive?view=powershell-5.1)). Размеры надо проверять до архивирования/публикации; это потенциальная проблема крупных сборок, а не доказанная причина текущего release. Общий PyInstaller spec широко собирает ML-пакеты и одновременно исключает модули; список hiddenimports сам по себе не доказывает полноту runtime. CPU-зависимости следует выбирать при установке, а не только вырезать CUDA-библиотеки из результата.

## MCP: совместимость и ошибки доступа

### Поддержка клиентов

Codex поддерживает stdio и Streamable HTTP; HTTP-конфигурация использует `mcp_servers` в TOML, `url` и `bearer_token_env_var`. Текущий Cursor JSON с `/sse` не является готовой конфигурацией Codex. [Официальная документация](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

Для подключения MCP к облачному ChatGPT документация предусматривает доступный HTTPS endpoint либо Secure MCP Tunnel; доступность зависит от workspace/account. Локальный `127.0.0.1` нельзя просто перенести в облачную настройку. [Официальная документация подключения](https://developers.openai.com/plugins/deploy/connect-chatgpt).

Минимальный совместимый путь: сохранить Cursor `/sse`, добавить `/mcp` с существующими vault-scoped обработчиками и экспорт Codex TOML. Для ChatGPT отдельно выбрать схему подключения и авторизации. Публиковать весь текущий HTTP app через туннель нельзя: он содержит административные методы без авторизации.

Существующий stdio может обмениваться MCP-сообщениями, но использует другой project-centric контекст; это не эквивалент scoped HTTP. `cursor-proxy` в `cli/commands.py:48-75` — заглушка с exit 1. В stdio `--project-root` лишь выводится в лог (`mcp_server/server.py:133`), а обработчик выбирает cwd. Реальный SDK-клиент это подтвердил.

### Критичные проблемы, воспроизведённые локально

| Проблема | Причина и доказательство |
|---|---|
| Пустой выбор папок открывает весь vault | UI создаёт `include: []` (`ScopesModal.ts:61`) и обещает отсутствие доступа (`:124`), но `scope_filter.py:9-15` разрешает любой путь |
| Glob может открыть соседнюю папку | `core/vault.py:23-31`: любая маска с `**`, заканчивающаяся `*.md`, пропускает все Markdown. `Projects/A/**/*.md` разрешил `Projects/B/secret.md`; `*.md` разрешил вложенную заметку |
| Admin API выдаёт scope-токены без авторизации | `http_app.py:114-133`, `admin_api.py:94-101`: анонимный GET scopes вернул 200 и полный token; tokenPreview не удаляет token |
| Индексация выходит за пределы vault | `admin_api.py:82-89`, `indexer.py:68-82`: анонимный POST с `../outside.md` вернул 200 и добавил искусственный внешний файл в индекс. Для проверки использовались fake embeddings/vector store |
| Scope B может отправлять сообщения в сессию A | `/messages/` проверяет лишь существование bearer, а не владельца session ID. В тесте смена bearer внутри открытой сессии сохранила scope A. Атакующему необходимо знать чужой session ID |

| Ошибка инструмента маркируется успехом | Отказ чтения вернулся JSON с error, но `CallToolResult.isError=false` |

До расширения подключений: исправить matcher и пустые scopes, ввести отдельную административную авторизацию, проверять realpath на всех входах индексатора и связывать session с principal. Для уже существующих scopes нужна явная совместимость/миграция; нельзя молча превратить намеренно широкий legacy scope в другой набор прав.

### Дополнительные подтверждённые замечания по коду

- `folderScope.ts:138-175`: снятие дочернего выбора при выбранном родителе не создаёт exclude; parent/** продолжает включать ребёнка.
- `vault_tools.py:119-126`: limit применяется до scope-фильтрации; видимые заметки могут существовать за пределами выбранных строк. Аналогично search ограничивает кандидатов до фильтрации.
- Sidecar health принимает любой HTTP 2xx без сверки vaultId; на Unix возможна остановка постороннего listener на заданном порте без доказательства принадлежности процессу. На Windows поиск listener PID не реализован.
- Restart может использовать сохранённый экземпляр SidecarManager со старыми настройками порта/команды.
- После старта удаляются listeners дочернего процесса; потеря мониторинга подтверждается кодом, блокировка pipe и видимая Windows-консоль требуют отдельной проверки в настоящем Obsidian.
- `Editor.create(overwrite=True)` и rename не выполняют обещанный backup; конкурентные правки не защищены общей блокировкой, временный файл имеет фиксированное имя. Конкурентная потеря данных в этом аудите не воспроизводилась.

## План минимальных изменений

1. **Исправить runtime и стабилизировать сборку.** Убрать ошибочное исключение unittest, исправить frozen CLI, проверить настоящую индексацию и отражение её ошибок. Привести Python lock/manifest к одному состоянию; закрепить инструменты сборки и поддерживаемые CPU wheels. Проверять exit codes в Windows, не принимать старый executable, использовать npm ci. Исправить dev-launch/PATH/.exe для Electron. Критерий: чистая Windows x64 сборка и запуск автономного binary.
2. **Закрыть нарушения доступа.** Однозначные empty/root/nested scope semantics, корректная сериализация дочерних исключений, административная capability, session-to-scope binding, свежая проверка прав, realpath до индексирования. Критерий: негативные тесты, включая обходы через admin/index/search и две одновременные scopes.
3. **Добавить Streamable HTTP рядом с SSE.** Использовать существующий MCP SDK и core, корректный lifespan и per-request auth; сохранить Cursor endpoint. Обновить минимальную версию SDK под реально используемые API; ошибки отдавать с isError и корректными tool annotations. Критерий: initialize/list/call/read/write и отказ доступа через оба транспорта.
4. **Добавить настройку Codex и определить подключение ChatGPT.** Экспорт TOML и инструкции по передаче scope-токена через переменную окружения. Для облачного ChatGPT — отдельная доступная HTTPS/Tunnel-схема только для защищённого MCP, без admin REST. Критерий: реальный вызов инструмента каждым целевым клиентом, сохранение работоспособности Cursor.
5. **Закрепить проверки в CI.** PR-проверки Python и обоих TS-пакетов; smoke готового executable с временным vault, индексацией и MCP-вызовом; проверка архитектуры и состава ZIP. Связать release assets с точным commit/tag и исключить смешение старых и новых частей.

Пункты следует выполнять отдельными небольшими изменениями, без смены стека. Исправление существующих lint/type ошибок отделять от добавления транспорта. ARM64, macOS/Linux, Electron installer и работа в реальном Obsidian требуют соответствующих сред; прохождение Windows x64 проверки их не заменяет.

## Состояние после исправлений (2026-09-29)

Исходные нарушения доступа и потери данных устранены в `f24301c`: пустая область запрещает чтение, сегментные glob не захватывают соседние папки, вход индексатора проверяется до чтения и пропуска неизменённого файла, поиск и список заметок не теряют разрешённые результаты из-за раннего лимита, правки заметок сохраняют резервную копию и сверяют хеш. Блокировка записи и проверка PID не завершают чужие процессы на Windows.

Локальный Streamable HTTP `/mcp`, отдельная административная capability, экспорт конфигурации и токена, привязка SSE-сессии к токену, проверка актуальных прав при вызове инструмента и исправления UI/stdio включены в `8dc1177`. Подключение облачного ChatGPT оставлено отдельной задачей: локальный HTTP-адрес не является общедоступным HTTPS endpoint.

Сборка и CI исправлены в `d4fd3d2`: lock-файл и CPU-зависимости согласованы, Windows native exit проверяется, готовый executable не заменяется устаревшим, а публикация релиза ждёт тестов и всех платформенных сборок. Локально прошли 45 Python-тестов (1 пропущен на Windows), 6 тестов плагина, Ruff, строгая проверка типов 60 Python-файлов, TypeScript typecheck и сборки плагина/Electron. Свежий Windows x64 executable прошёл проверку нативных импортов, проиндексировал искусственный vault и прочитал заметку через MCP. Windows release ZIP собран и содержит ожидаемые пять файлов.
